# Agent Note: 面向目标的会话交接

Status: proposed

[English](2026-11-06-session-handoff.md) | 中文

## 问题

长会话会积累目标、决策与工作集，但开启新会话会把它们全部丢弃：新 agent 必须重新发现任务，操作者也不得不手动重复。Fork 会话能避免重复，却把完整历史复制进请求，子会话从第一步就承担父会话的全部上下文成本。先就地压缩再继续会改动父会话，并替换操作者可能仍需要的历史。计划的交接方向（P5）要求第三条路径：结构化、面向目标的检查点，加上与父会话链接的新会话，使子会话从小上下文开始，同时仍能通过既有工具访问完整历史。

## 方案

`@deepseek-ai/dsh-handoff` 注册 `/handoff <goal>`。命令读取实时会话投影（`session.deriveMessages()`），用 token meter 测量上下文，并渲染有界检查点：先目标，再父会话 id 与实测 token 数，然后是最后请求与最后结果、带边界参数的最近工具调用、引用文件，以及命名 `session_event_search` 与 `session_trace` 及父 id 的固定指引。它创建 `header.parentSession` 指向父会话的子会话，追加 `turn/start` 与一条标记为 `handoff-checkpoint` 的用户消息，并报告子会话 id 与实测 token 数。父会话不被 fork、压缩或删除。

继续性门禁（确定性代理，不运行模型）：三个继续任务、每个五个事实。检查点携带 **15/15 个事实**（recall 1,00），因此子会话需要 **0 次恢复搜索**；没有交接的子会话需要 **15 次**（每个缺失事实一次）。六个聚焦测试覆盖检查点边界、链接子会话创建、父会话不可变性、用法校验、token 报告与门禁。已发布预设中未挂载任何内容，因此已记录快照不变。

## 已考虑的替代方案

- **把父会话 fork 成子会话** — 拒绝：子会话继承完整历史及其上下文成本，而交接正是为了避免这一点。
- **就地压缩后再继续** — 拒绝：改动父会话并销毁操作者可能仍需要的历史；压缩已作为独立命令存在。
- **模型撰写的交接摘要** — 拒绝：为机械操作增加成本、延迟与非确定性；检查点是确定性派生，父日志仍是权威。
- **仅前端的会话复制** — 拒绝：没有持久的 `parentSession` 链接，子日志中也没有检查点消息。

## 验收标准

- `/handoff <goal>` 创建带 `header.parentSession` 的子会话、首条消息包含检查点与父指引，并保持父会话历史不变。
- 检查点保持在配置边界内，并且始终命名父 id 与会话工具。
- 继续性门禁报告 recall 与恢复步骤数字；空目标返回用法错误且不创建会话。
- 聚焦测试、typecheck 与文档门禁通过；在编排中启用是单独的属主决策。

## 风险

- **代理门禁** — 恢复步骤按缺失事实计数，而非模型实跑；该数字是内部信号，实跑评估仍是启用门槛。
- **检查点丢失** — 超出有界最后交互与工作集的细节不会被携带；指引指向父日志，而不是假装完整。
- **操作者流程** — 命令不切换界面；操作者打开报告的子会话。
- **父会话保留** — 不自动处置或压缩父会话；保留由操作者决定。
